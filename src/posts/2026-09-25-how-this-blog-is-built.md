## The whole architecture

```
src/posts/*.md  --[pandoc]-->  HTML fragment  --[build.mjs + layout]-->  docs/*.html
```

The entire build dependency is `pandoc` plus a single Node script that uses nothing but the standard library. There is no `node_modules`, no bundler, no framework — and the browser receives **zero JavaScript**.

## Repository layout

```
blog/
├── site.json                 site title, author, base URL
├── build.mjs                 the build script
├── filters/sidenotes.lua     footnote -> margin note
├── templates/layout.html     page skeleton
├── assets/
│   ├── style.css             all styling
│   └── fonts/et-book/        the text typeface
├── src/posts/                your Markdown
└── docs/                     build output (published)
```

## Why Pandoc

After trying the usual static site generators, this came down to three concrete properties:

1. **Math works out of the box.** `--mathml` emits real MathML, which browsers have rendered natively since Chromium 109. No KaTeX, no MathJax, no half-megabyte of runtime.
2. **Highlighting happens at build time.** Skylighting tags each token with a class, so colour is entirely a CSS concern — which is what makes light and dark themes a single stylesheet instead of two.
3. **The Markdown dialect is strong enough.** GFM plus math extensions covers tables, task lists, footnotes, and definition lists, and matches what GitHub renders for the same file.

## How the build works

Each post is compiled twice by Pandoc: once to JSON to read the front matter, once to HTML for the body. Then a handful of post-processing steps run on the output:

```js
// Block math arrives wrapped in a paragraph; unwrap it so it can be
// laid out at the column width rather than inheriting paragraph margins.
html = html.replace(/<p>(<math display="block"[\s\S]*?<\/math>)<\/p>/g, '$1');

// Tables get a scroll container so wide ones don't break the layout on phones.
html = html.replace(/<table(\s|>)/g, '<div class="table-wrapper"><table$1')
           .replace(/<\/table>/g, '</table></div>');
```

Footnotes are converted to Tufte-style margin notes by a Lua filter, which runs inside Pandoc — so no extra tooling is involved. The filter operates on the AST rather than on rendered HTML, which means the notes end up in the correct position by construction instead of by regex surgery.

## The trade-offs

Being honest about what this gives up:

- **No theme ecosystem.** Styling is one CSS file you own end to end.
- **No built-in features.** Tags, the archive, and the feed are generated by about sixty lines of string concatenation in `build.mjs`. Easy to change, and yours to maintain.
- **Pandoc's dialect is wider than GFM.** Syntax that Pandoc understands but GitHub does not will render on the site and break in the repository view. Worth knowing when a post is meant to be readable in both places.

> For a personal blog, that trade buys something worth having: no build cache to clear, no plugin conflicts to debug, no major-version migration to schedule.
